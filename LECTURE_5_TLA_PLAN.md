# БЛОК 1. Зачем всё это (00–15). Только доска, без кода

## 1.1. Задача, которую все понимают

Нарисуйте на доске:

```text
   Клиенты                 Шлюз (API Gateway)                Бэкенд
  ┌──────┐                ┌────────────────────┐            ┌──────┐
  │  c1  │ ─────────────> │ лимит: 5 сессий    │ ─────────> │  БД  │
  │  c2  │ ─────────────> │ счётчик: active    │            │      │
  │ ...  │ ─────────────> │                    │            │      │
  │  c20 │ ─────────────> │ 6-й → 429 Too Many │            │      │
  └──────┘                └────────────────────┘            └──────┘
```

**Говорим простыми словами:**
> «Шлюз защищает бэкенд: внутрь одновременно пускаем не больше 5 клиентов. Это **политика безопасности**: защита от DoS, от брутфорса, от исчерпания соединений к БД. Логика очевидна: *проверь, есть ли место; если есть, пусти и увеличь счётчик*».

## 1.2. Где прячется уязвимость

Напишите на доске псевдокод:

```text
if (active < 5)        ← ПРОВЕРКА   (Time of Check)
    ... проверяем JWT, пишем лог ...   ← окно
    active = active + 1  ← ДЕЙСТВИЕ (Time of Use)
```

Нарисуйте два потока во времени:

```text
время ──────────────────────────────────────────────────────>
Поток A:  [проверка: 4<5 ✔]  ......окно......  [active = 5]
Поток B:        [проверка: 4<5 ✔]  ...окно...        [active = 6]  ← ЛИМИТ ПРОБИТ
```

> «Оба потока проверили условие, когда место ещё было. Потом оба вошли. Решение принято по **устаревшему** состоянию мира. Это **TOCTOU** (Time-of-Check to Time-of-Use, CWE-367), частный случай **Race Condition** (CWE-362).
> Для безопасника это не просто «баг»: так обходят лимиты попыток ввода пароля, дважды списывают деньги с одного баланса (double spending) и активируют один промокод сто раз».

## 1.3. Почему тесты это не ловят

> «Unit-тест вызывает метод последовательно: 1, 2, 3, 4, 5, 6 → шестой получает 429. Тест зелёный.
> Баг проявляется только при **определённом порядке переключения потоков**, а этот порядок выбирает планировщик ОС, не мы».

Запишите на доске:

```text
2 потока по 3 шага   →  20 возможных порядков выполнения
10 потоков по 5 шагов →  ~10^43 порядков

Тест проверяет ОДИН порядок за запуск.
Атакующий шлёт 10 000 запросов одновременно и ждёт, пока выпадет «плохой».
```

Цитата Дейкстры: **«Тестирование может показать наличие ошибок, но не их отсутствие»**.

## 1.4. «Ну так поставим lock, и всё»: ключевой вопрос лекции

Студенты обязательно это скажут. Ответ из четырёх пунктов (запишите на доске):

1. **lock — это лекарство, а не диагноз.** Сначала нужно понять, *что именно* должно быть атомарным. Заметный пример: если заменить `active++` на `Interlocked.Increment`, уязвимость **останется**, потому что сам инкремент атомарен, а *проверка + инкремент* вместе нет. Ошибка в *проекте*, а не в строчке.
2. **lock надо доказать.** Поставили lock, тесты зелёные. Но зелёные тесты ничего не доказывают (п. 1.3). Где гарантия, что lock стоит в правильном месте и нигде нет второго пути к счётчику?
3. **lock порождает новые проблемы:** deadlock, голодание, падение пропускной способности. Их тоже нужно проверять (это лекция 7).
4. **В распределённой системе lock нет.** Если за балансировщиком стоят 3 экземпляра шлюза, а счётчик хранится в Redis или PostgreSQL, то `lock` в C# защищает только свой процесс. Нужен *протокол*, и правильность протокола нельзя проверить ни компилятором, ни юнит-тестом.

```text
          ┌─ Шлюз #1 (свой lock) ─┐
nginx ────┼─ Шлюз #2 (свой lock) ─┼──> Redis: active = ?   ← lock тут бесполезен
          └─ Шлюз #3 (свой lock) ─┘
```

> **Вывод блока:** «TLA+ не конкурент lock-у. TLA+ — это инструмент, который **до написания кода** перебирает *все* порядки шагов, находит тот, что ломает безопасность, показывает его пошагово, а после исправления доказывает (для заданного размера модели), что плохих порядков больше нет. А lock, CAS, `SELECT ... FOR UPDATE` — это способы реализовать уже проверенное решение».

# БЛОК 2. Что такое TLA+ и TLC (15–25). Доска

## 2.1. Три названия, которые путают

| Название | Что это | Аналогия из .NET |
|---|---|---|
| **TLA+** | Язык, на котором описываем систему математически | Язык C# |
| **TLC** | Программа-проверяльщик (model checker), перебирает все состояния | Компилятор + тест-раннер, только перебирает *всё* |
| **TLA+ Toolbox** / расширение VS Code | IDE для TLA+ | Rider |

Автор — **Лесли Лэмпорт** (премия Тьюринга 2013, Paxos, логические часы, LaTeX). Применяют в Amazon (S3, DynamoDB), Microsoft (Azure Cosmos DB), Intel, MongoDB.

## 2.2. Главная идея: система = состояния + переходы

> «В C# мы пишем **инструкции**: сделай это, потом то. В TLA+ мы описываем **какие бывают состояния** и **какие шаги разрешены** между ними. Порядок шагов мы не задаём, его перебирает TLC».

Аналогия с шахматами:
> «Правила шахмат не говорят, как играть партию. Они говорят: вот начальная расстановка, вот допустимые ходы. А TLC — компьютер, который переберёт **все возможные партии** и найдёт ту, где король оказался под ударом, хотя не должен».

```text
   Init (расстановка)       Next (допустимые ходы)        Инвариант (правило «король не под ударом»)
        │                          │                                 │
        ▼                          ▼                                 ▼
   [s0] ──ход──> [s1] ──ход──> [s2] ──ход──> [s3]  ← TLC проверяет инвариант в КАЖДОМ состоянии
          └──ход──> [s4] ──ход──> [ПЛОХОЕ]  ← нашёл → печатает путь s0 → s4 → ПЛОХОЕ
```

**Состояние** — снимок всех переменных в момент времени: `{ active = 2, c1 = "in_session", c2 = "idle" }`.

## 2.3. Два файла: `.tla` и `.cfg`

> «Это как класс и `appsettings.json`».

| Файл | Отвечает на вопрос | Аналогия |
|---|---|---|
| `Spec.tla` | **Что** это за система: переменные, начальное состояние, шаги, свойства | Код класса |
| `Spec.cfg` | **Как** проверять: с какими конкретными значениями констант и какие свойства проверять | `appsettings.json` + выбор тестов |

Почему они разделены: в `.tla` мы пишем «есть множество клиентов `Clients` и лимит `MaxSessions`» в общем виде. А в `.cfg` говорим TLC: «проверь для 3 клиентов и лимита 2». TLC умеет проверять только **конечные** модели, поэтому конкретные значения обязательны.

# БЛОК 3. Live: пример 1 «Часы» (25–40)

> **Зачем этот пример:** на нём видно весь синтаксис без отвлечения на многопоточность. Пять строк кода показывают `Init`, `Next`, штрих и инвариант.

## 3.1. Создаём файл `tla/Ex1_Clock.tla`

Пишем по частям и комментируем каждую строку.

**Шаг 1. Рамка модуля**
```tla
---------------------------- MODULE Ex1_Clock ----------------------------

=============================================================================
```
> «Строка из минусов с `MODULE Имя` открывает модуль, строка из `=` закрывает. **Имя модуля обязано совпадать с именем файла**, иначе TLC не запустится. Количество минусов не важно, нужно минимум четыре».

**Шаг 2. Подключаем библиотеку чисел**
```tla
EXTENDS Naturals
```
> «Это как `using System;`. Без `Naturals` TLA+ не знает, что такое `+`, `<` и `1..12`. Позже понадобятся `FiniteSets` (размер множества `Cardinality`) и `Integers` (отрицательные числа)».

**Шаг 3. Переменная состояния**
```tla
VARIABLE hour
```
> «Переменные **без типа**. Тип мы потом проверим инвариантом. Переменные — это всё, что меняется со временем».

**Шаг 4. Начальное состояние**
```tla
Init == hour = 1
```
> «Два символа равенства, и это важно:
> - `==` значит **«определяю имя»**. `Init == ...` читается как «Init по определению есть ...». Похоже на объявление метода без параметров.
> - `=` значит **сравнение**, как `==` в C#. Не присваивание!
>
> То есть `Init` — это **условие**, а не действие: «стартовое состояние — то, где hour равно 1».

**Шаг 5. Шаг системы и штрих**
```tla
Next == hour' = IF hour = 12 THEN 1 ELSE hour + 1
```
> «Главный синтаксический элемент TLA+ — **штрих** `'`.
> - `hour` — значение **сейчас**,
> - `hour'` — значение **в следующем состоянии**.
>
> `hour' = hour + 1` — это не `hour = hour + 1` из C#. Это утверждение: «переход разрешён, если новое hour на единицу больше старого». `Next` описывает **какие пары (старое состояние, новое состояние) допустимы**».

**Шаг 6. Инвариант**
```tla
TypeOK == hour \in 1..12
```
> «`\in` — математическое ∈, «принадлежит». `1..12` — множество {1, 2, ..., 12}. Инвариант — условие, которое должно быть истинно **в каждом** достижимом состоянии. `TypeOK` — общепринятое имя для проверки типов, раз в языке нет типов».

## 3.2. Создаём `tla/Ex1_Clock.cfg`

```text
INIT Init
NEXT Next
INVARIANT TypeOK
```
> «Говорим TLC: начальное состояние ищи в определении `Init`, шаг — в `Next`, в каждом состоянии проверяй `TypeOK`. Здесь пишутся **имена** определений из `.tla`, а не формулы».

## 3.3. Запускаем

```powershell
powershell -ExecutionPolicy Bypass -File .\tla\run_tlc.ps1 -Spec Ex1_Clock
```

Ожидаемый вывод:
```text
Model checking completed. No error has been found.
13 states generated, 12 distinct states found, 0 states left on queue.
The depth of the complete state graph search is 12.
```

Как читать:
- **distinct states = 12**: TLC нашёл ровно 12 разных состояний (часы 1..12). Перебор полный.
- **states generated = 13**: всего переходов посчитано (переход 12→1 привёл в уже известное состояние 1).
- **depth = 12**: самая длинная цепочка шагов от старта.
- **0 states left on queue**: непроверенных состояний не осталось, то есть перебор завершён.

## 3.4. Ломаем вживую (самый важный момент блока)

Меняем `Next` на «наивный» вариант и запускаем снова:
```tla
Next == hour' = hour + 1
```
Вывод:
```text
Error: Invariant TypeOK is violated.
State 1: hour = 1
State 2: hour = 2
...
State 13: hour = 13      ← нарушение
```
> «TLC не просто сказал «ошибка». Он **показал путь**: 12 шагов, на 13-м часы показывают 13. Это называется **трасса контрпримера** (error trace). Для безопасника это готовый сценарий эксплойта».

Возвращаем `IF ... THEN ... ELSE` и убеждаемся, что ошибок снова нет.

# БЛОК 4. Live: пример 2 «Потерянное обновление» (40–52)

> **Зачем этот пример:** это мостик от часов к шлюзу. Задача знакома с лекции 3 (`Interlocked`): почему `counter++` из двух потоков даёт не 2, а иногда 1. Здесь появляются **несколько потоков**, **недетерминизм** и **массивы** в TLA+.

## 4.1. Рассказываем идею (доска)

```text
C#:  counter++;
CPU: 1) tmp = counter      (прочитать в регистр)
     2) counter = tmp + 1  (записать обратно)

Поток t1: tmp1 = 0 ............ counter = 1
Поток t2:        tmp2 = 0 .............. counter = 1    ← одно обновление потеряно
```

> «Чтобы описать это в TLA+, нужно моделировать **каждый шаг процессора как отдельный переход**. А чтобы знать, на каком шаге стоит каждый поток, заведём переменную `pc` (program counter), как указатель инструкции».

## 4.2. Пишем `tla/Ex2_LostUpdate.tla`

**Константы и переменные**
```tla
EXTENDS Naturals, FiniteSets

CONSTANT Threads            \* множество потоков; значение задаётся в .cfg

VARIABLES x, tmp, pc
vars == <<x, tmp, pc>>
```
> - `CONSTANT` — параметр модели. Значение не пишем здесь, оно в `.cfg`. Как параметр конструктора.
> - `\*` — комментарий до конца строки (`//` в C#). `(* ... *)` — многострочный (`/* */`).
> - `<<x, tmp, pc>>` — **кортеж** (tuple). Нужен, чтобы коротко написать «все переменные не изменились».

**Начальное состояние, функции (массивы)**
```tla
Init ==
    /\ x   = 0
    /\ tmp = [t \in Threads |-> 0]
    /\ pc  = [t \in Threads |-> "read"]
```
> - `/\` — **логическое И** (`&&`). Список с `/\` в начале строк читается как маркированный список условий, и **все** должны быть истинны. Отступы важны: пункты одного списка выравниваются по одной колонке.
> - `[t \in Threads |-> 0]` — **функция** (по сути `Dictionary<Thread, int>`): «каждому потоку t сопоставить 0». Если `Threads = {t1, t2}`, получится `{ t1: 0, t2: 0 }`.
> - Обращение к элементу: `pc[t]`, как в C#.

**Шаг «чтение»: EXCEPT и UNCHANGED**
```tla
Read(t) ==
    /\ pc[t] = "read"                          \* охранное условие
    /\ tmp' = [tmp EXCEPT ![t] = x]            \* tmp[t] := x
    /\ pc'  = [pc  EXCEPT ![t] = "write"]
    /\ UNCHANGED x
```
> Объясняем три новые вещи:
> 1. **Охранное условие (guard).** Первая строка без штриха — это «когда шаг разрешён». Если `pc[t]` не равно `"read"`, действие `Read(t)` просто невозможно. Аналог `if` в начале метода.
> 2. **`[f EXCEPT ![k] = v]`** — «копия функции f, где по ключу k лежит v». В TLA+ нельзя написать `tmp[t]' = x`; нужно описать **новую функцию целиком**. Аналог в C#: `dict with { [t] = x }` или `new Dictionary(dict) { [t] = x }`.
> 3. **`UNCHANGED x`** = `x' = x`. **Самая частая ошибка новичков.** В C# незатронутая переменная сохраняет значение сама. В математике, если вы ничего не сказали про `x'`, оно может быть **любым**. Поэтому в каждом действии нужно сказать что-то про **каждую** переменную. Если забыть, TLC выдаст ошибку о том, что следующее состояние задано не полностью.

**Шаг «запись»**
```tla
Write(t) ==
    /\ pc[t] = "write"
    /\ x'  = tmp[t] + 1
    /\ pc' = [pc EXCEPT ![t] = "done"]
    /\ UNCHANGED tmp
```

**Завершение и Next: недетерминизм**
```tla
Finished ==
    /\ \A t \in Threads : pc[t] = "done"
    /\ UNCHANGED vars

Next == (\E t \in Threads : Read(t) \/ Write(t)) \/ Finished
```
> - `\/` — **логическое ИЛИ** (`||`).
> - `\E t \in Threads : ...` — «**существует** поток t, для которого...». Вот где появляется **планировщик ОС**: TLC перебирает *каждый* поток и *каждое* разрешённое действие. Мы не говорим, кто ходит первым; TLC проверит все варианты.
> - `\A t \in Threads : ...` — «**для всех** потоков».
> - `Finished` нужен, чтобы после завершения всех потоков система могла «стоять на месте». Иначе TLC сообщит **Deadlock**: ни одно действие не разрешено. (Альтернатива: строка `CHECK_DEADLOCK FALSE` в `.cfg`.)

**Свойство корректности**
```tla
NoLostUpdate ==
    (\A t \in Threads : pc[t] = "done") => x = Cardinality(Threads)
```
> «`=>` — импликация: «*если* все закончили, *то* x равно числу потоков». Пока потоки работают, условие истинно автоматически. `Cardinality` — размер множества (из `FiniteSets`)».

## 4.3. Пишем `tla/Ex2_LostUpdate.cfg`

```text
INIT Init
NEXT Next
CONSTANTS
    Threads = {t1, t2}
INVARIANT NoLostUpdate
```
> «`t1`, `t2` — это **model values**: просто уникальные метки без значения, как `enum`. Объявлять их нигде больше не нужно».

## 4.4. Запускаем и читаем трассу

```powershell

```

```text
State 1: <Initial predicate>   x = 0, pc = (t1 :> "read"  @@ t2 :> "read")
State 2: <Read(t1)>            x = 0, pc = (t1 :> "write" @@ t2 :> "read"),  tmp t1 = 0
State 3: <Read(t2)>            x = 0, pc = (t1 :> "write" @@ t2 :> "write"), tmp t2 = 0
State 4: <Write(t1)>           x = 1
State 5: <Write(t2)>           x = 1   ← оба закончили, а x = 1, не 2
```
> Как читать формат: `(t1 :> "read" @@ t2 :> "read")` — это функция `{ t1 → "read", t2 → "read" }`. В угловых скобках имя действия, которое привело в это состояние.

## 4.5. Чиним вживую («это и есть Interlocked.Increment»)

Заменяем `Read` и `Write` одним атомарным действием:
```tla
Inc(t) ==
    /\ pc[t] = "read"
    /\ x'  = x + 1
    /\ pc' = [pc EXCEPT ![t] = "done"]
    /\ UNCHANGED tmp

Next == (\E t \in Threads : Inc(t)) \/ Finished
```
Запускаем: `No error has been found`.

> **Ключевая мысль, которую надо проговорить:** «**Атомарность в TLA+ = одно действие.** Всё, что внутри одного действия, происходит мгновенно и неделимо. Если операция в коде разбита на два действия, между ними может вклиниться любой другой поток. Значит, при моделировании главный вопрос: **что в моём коде на самом деле атомарно?**»

(После демонстрации верните файл к исходной версии через Ctrl+Z, чтобы потом можно было повторить.)

# БЛОК 6. Live: модель шлюза в TLA+ (60–78)

## 6.1. Сначала таблица соответствия (доска)

> «Прежде чем писать, переведём C# в термины состояний и переходов».

| C# | TLA+ | Почему так |
|---|---|---|
| поле `_maxSessions` | `CONSTANT MaxSessions` | не меняется во время работы |
| набор клиентов | `CONSTANT Clients` | параметр модели (в `.cfg`: `{c1,c2,c3}`) |

```text
 "idle" ──────────────> "checked" ──────────────> "in_session"
```

## 6.2. Пишем `tla/GatewayRateLimiter_Buggy.tla` по частям

## 7.1. Исправляем модель (`GatewayRateLimiter_Fixed.tla`)

## 7.2. Переносим в C# (`SecureGateway.cs`)

> «Теперь мы знаем, **что** должно быть атомарным: проверка + инкремент. Осталось выбрать **как** реализовать атомарность в .NET».

```csharp
while (true)
{
    int current = Volatile.Read(ref _activeSessions);
    if (current >= _maxSessions)
        return false;

    // Записать current+1, ТОЛЬКО если значение всё ещё current
    if (Interlocked.CompareExchange(ref _activeSessions, current + 1, current) == current)
        return true;

    // Кто-то успел изменить счётчик → наша проверка устарела → проверяем заново
}
```
> «Почему это соответствует одному действию TLA+? `CompareExchange` атомарно проверяет, что счётчик не изменился с момента нашей проверки. Если изменился, запись не происходит и мы повторяем проверку. Значит, **успешный** инкремент всегда опирается на актуальную проверку».

Варианты реализации того же решения (проговорить):
- `lock { if (...) ...; active++; }` — проще, но медленнее под нагрузкой;
- `SemaphoreSlim(5)` + `Wait(0)` — идиоматичный .NET-способ для этой задачи;
- в распределённом варианте: `UPDATE limits SET active = active + 1 WHERE active < 5` в PostgreSQL (одна атомарная команда) или атомарный скрипт в Redis. Это модуль 3 курса.

> «Все четыре способа реализуют **одну и ту же** проверенную модель. TLA+ сказал нам, *что* делать; lock или CAS — *чем* это сделать».

Запуск: `dotnet run`, пункт **2**:
```text

СТАТУС: Інваріант безпеки втримано (0 порушень).
```

# БЛОК 8. Итоги (86–90)

1. Race condition и TOCTOU — это ошибки **проекта**, а не синтаксиса. Тесты их не находят, потому что проверяют один порядок шагов из огромного числа.
2. TLA+ описывает систему как **состояния + переходы**; TLC перебирает **все** порядки и выдаёт трассу атаки.
3. Главное правило моделирования: **одно действие TLA+ = одна атомарная операция в коде**.
4. lock и TLA+ не конкуренты: TLA+ находит, *что* должно быть атомарным, и проверяет решение; lock/CAS/SQL это решение реализуют.

**Честно об ограничениях (магистрам это важно):**
- TLC проверяет **конечную** модель (3 клиента, лимит 2). Это сильный аргумент, но не доказательство для любого N.
- TLC проверяет **модель**, а не C#-код. Если модель не соответствует коду (например, мы посчитали атомарным то, что не атомарно), проверка ничего не гарантирует.

**Дальше:** лекция 6 — инварианты и взаимное исключение; лекция 7 — liveness («что-то хорошее когда-нибудь случится»), deadlock и голодание; **лабораторная №3** — модель алгоритма взаимного исключения в TLA+.

# ПРИЛОЖЕНИЕ A. Шпаргалка синтаксиса TLA+ (можно вывести на слайд)

| TLA+ | Смысл | Аналог в C# |
|---|---|---|
| `---- MODULE X ----` … `====` | начало и конец модуля (имя = имя файла) | `namespace` / файл |
| `EXTENDS Naturals, FiniteSets` | подключить модули | `using` |
| `CONSTANT N` / `CONSTANTS A, B` | параметры модели (значения в `.cfg`) | параметры конструктора |
| `VARIABLE x` / `VARIABLES x, y` | переменные состояния | поля класса |
| `Name == expr` | определение | объявление метода/свойства |
| `Op(a) == expr` | определение с параметром | метод с параметром |
| `=` | равенство (сравнение!) | `==` |
| `#` или `/=` | не равно | `!=` |
| `x'` | значение x в следующем состоянии | — |
| `/\` | И | `&&` |
| `\/` | ИЛИ | `\|\|` |
| `~` | НЕ | `!` |
| `=>` | если …, то … | `!a \|\| b` |
| `\in` | принадлежит множеству | `set.Contains(x)` |
| `1..5` | множество {1,2,3,4,5} | `Enumerable.Range(1,5)` |
| `{"a", "b"}` | множество | `HashSet` / `enum` |
| `\A x \in S : P` | для всех x из S верно P | `S.All(x => P)` |
| `\E x \in S : P` | существует x из S, для которого P | `S.Any(x => P)` |
| `[x \in S \|-> e]` | функция: каждому x сопоставить e | `S.ToDictionary(x => x, x => e)` |
| `f[x]` | значение функции | `dict[x]` |
| `[f EXCEPT ![k] = v]` | копия f, где по ключу k лежит v | `new Dictionary(f) { [k] = v }` |
| `<<a, b>>` | кортеж | `(a, b)` |
| `UNCHANGED x` / `UNCHANGED <<x, y>>` | `x' = x` (и `y' = y`) | — |
| `IF c THEN a ELSE b` | условное выражение | `c ? a : b` |
| `Cardinality(S)` | размер множества (`FiniteSets`) | `S.Count` |
| `\* текст` | комментарий до конца строки | `// текст` |
| `(* текст *)` | многострочный комментарий | `/* текст */` |

**Как читать списки `/\` и `\/`:**
```tla
A ==
    /\ P          \* A истинно, если истинны P, Q и R одновременно
    /\ Q
    /\ R
```
Пункты одного списка выравниваются по одной колонке. Это заменяет скобки.

**Анатомия действия** (шаблон, по которому пишется любое действие):
```tla
ИмяДействия(параметр) ==
    /\ <охранные условия БЕЗ штрихов>      \* КОГДА шаг разрешён
    /\ <переменная' = новое значение>      \* ЧТО меняется
    /\ UNCHANGED <<остальные переменные>>  \* ЧТО НЕ меняется (обязательно для всех остальных!)
```

# ПРИЛОЖЕНИЕ B. Шпаргалка по файлу `.cfg`

# ПРИЛОЖЕНИЕ C. Как читать вывод TLC

| Строка вывода | Что значит |
|---|---|
| `No error has been found` | все достижимые состояния проверены, свойства выполняются |
| `Invariant X is violated` | найдено состояние, где X ложно; ниже трасса |
| `State N: <Действие(арг)>` | состояние N, в которое пришли действием `Действие` |
| `(c1 :> "idle" @@ c2 :> "checked")` | функция `{ c1 → "idle", c2 → "checked" }` |
| `distinct states found` | сколько разных состояний найдено |
| `states generated` | сколько переходов посчитано (включая повторы) |
| `depth` | длина самой длинной цепочки шагов |
| `states left on queue` | сколько состояний осталось непроверенными (если ошибка найдена, перебор остановлен) |
| `Deadlock reached` | достигнуто состояние, из которого не разрешено ни одно действие |

**Частые ошибки на живом кодинге:**

| Симптом | Причина |
|---|---|
| Ошибка парсинга в конце файла | забыта закрывающая строка `====` |
| Модуль не находится | имя после `MODULE` не совпадает с именем файла |
| `Unknown operator: Cardinality` | не подключён `FiniteSets` в `EXTENDS` |
| Ошибка «следующее состояние задано не полностью» / переменная не присвоена | в каком-то действии забыт `UNCHANGED` для одной из переменных |
| `Deadlock reached` | ни одно действие не разрешено (добавить действие-«остановку» или `CHECK_DEADLOCK FALSE`) |
| Ошибка в `.cfg` «expecting a keyword» | опечатка в ключевом слове (`INIT`, `NEXT`, `CONSTANTS`, …) |
